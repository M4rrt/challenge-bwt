# 25 — Infra hardening: frontend hosting, autoscaling, NAT, DNS, remote state

**What to build:** Close four gaps found in a review of `infra/`: no frontend hosting (the SPA has nowhere to run in production), no backend autoscaling (`backend_desired_count` is fixed), no DNS (only the ALB's automatic DNS name), and no remote Terraform state backend (state is local — unworkable with more than one person applying). The fifth gap, the missing NAT Gateway, is deliberately **not** built here — see the NAT Gateway item below for why provisioning it now would be dead cost, and what it's actually blocked on. Same validation approach as the rest of `infra/`: write correct, `terraform validate`/`plan`-clean Terraform, apply best-effort against LocalStack community, and document any Pro-tier gaps the same way ADR-0003/ticket 11 did for ECS/ECR/RDS/ElastiCache/ALB. No real AWS account or registered domain is assumed.

**Blocked by:** 02, 11.

**Status:** done

- [x] `frontend.tf`: private S3 bucket for the SPA build output + CloudFront distribution in front of it, using Origin Access Control (bucket has no public access, only reachable via CloudFront) — expect CloudFront to hit the same LocalStack Pro-tier wall as ALB/ECS/RDS; document it in `infra/README.md`'s "Known limitation" section alongside the existing five
- [x] CloudFront configured for SPA client-side routing (403/404 from S3 → serve `/index.html` with 200) so React Router deep links work
- [x] A documented/scripted step builds the frontend (`npm run build` in `frontend/`) and uploads `dist/` to the new S3 bucket (e.g. `aws s3 sync`, targeted at the LocalStack endpoint for local validation) — `infra/scripts/deploy-frontend.sh`
- [x] `backend/Dockerfile` — closes the gap `infra/README.md` currently documents ("there's no Dockerfile yet"); builds the FastAPI backend image
- [x] A documented/scripted step builds that image and pushes it to the existing `aws_ecr_repository.backend`, tagged with the git commit SHA (not `latest` — `var.image_tag` still defaults to `latest` for convenience, but the documented push step uses `git rev-parse --short HEAD` so deploys are reproducible/rollback-able) — `infra/scripts/push-backend-image.sh`
- [x] `autoscaling.tf`: `aws_appautoscaling_target` for `aws_ecs_service.backend` (`min_capacity` = 1, `max_capacity` = 3) with two `aws_appautoscaling_policy` target-tracking policies — `ECSServiceAverageCPUUtilization` and `ECSServiceAverageMemoryUtilization`
- [x] **NAT Gateway: not built in this ticket.** A NAT Gateway costs ~$32+/month running idle, and today nothing would use the private route — RDS/ElastiCache don't need egress, and ECS still runs in the public subnets (ticket 02's design, unchanged here; moving it to private subnets is a separate security-hardening ticket, explicitly out of scope). Provisioning an orphaned NAT now is cost with no payoff. Instead: `infra/README.md` gets a short "Known gap" note recording this decision and stating the NAT Gateway ships together with the future "move ECS to private subnets" ticket, not before it
- [x] `acm.tf`: `aws_acm_certificate` for `var.domain_name` in `us-east-1` (required region for CloudFront regardless of where the rest of the stack runs), with DNS validation records in the Route53 zone below — CloudFront cannot serve a custom domain without this, so it's part of the DNS/CloudFront setup, not optional polish
- [x] `dns.tf`: `var.domain_name` (placeholder default, e.g. `chat-app.example.com`), `aws_route53_zone`, an ALIAS record to the ALB, and an ALIAS (or CNAME) record to the CloudFront distribution — CloudFront's `aliases`/`viewer_certificate` reference the ACM cert above; note the ALB itself stays HTTP-only (no listener/cert change here), so `chat-app.example.com` gets TLS via CloudFront but the API/WS path behind the ALB record does not — call this out explicitly in `infra/README.md` as a known gap, not silently shipped as "DNS done"
- [x] `infra/bootstrap/`: separate, self-contained Terraform config with its own local state (it provisions its own backend's dependencies, so it can't use that backend itself) creating a versioned S3 bucket and a DynamoDB lock table for the main `infra/` state
- [x] `infra/provider.tf` gets a `backend "s3"` block (or documented `-backend-config` flags) pointing at the bootstrap bucket/table, with LocalStack endpoint overrides for local validation
- [x] `infra/README.md` documents: how to run `infra/bootstrap/` once, how the main `infra/` then initializes against that backend, and any new Pro-tier gaps found (CloudFront, Route53, Application Auto Scaling, NAT Gateway) the same way the existing five are documented
- [x] `terraform validate` and `terraform plan` pass cleanly for both `infra/` and `infra/bootstrap/`; `terraform apply` attempted against LocalStack for both, with results (success/Pro-tier failure) recorded in `infra/README.md` — note in the same section that this only proves the S3-backend *mechanism* initializes and locks against a single local container, not that it solves multi-person concurrent applies, since that scenario needs a real shared AWS account to actually exercise
- [x] After each fix in this ticket is applied, update the doc that described the gap (`infra/README.md`, `docs/architecture.md` from ticket 12, and/or the relevant ADR) to note it was addressed by ticket 25 — same pattern ADR-0003 already uses to reference ticket 11 — so the docs stay in sync with the project's current state instead of describing gaps that no longer exist

## Comments

**2026-08-09** — Implemented and validated end-to-end against a live LocalStack container (Terraform v1.15.8, `hashicorp/aws` 5.100.0, LocalStack community 3.8.1, isolated on port 4599 to avoid an unrelated LocalStack instance already running on the host's 4566).

- `infra/bootstrap/`: `terraform init`/`apply` succeeded — versioned S3 bucket + DynamoDB lock table (`PAY_PER_REQUEST`, hash key `LockID`) both created cleanly. Hit one real bug along the way: `aws_s3_bucket` creation hung indefinitely retrying a malformed `HEAD /` request against LocalStack's edge router — LocalStack doesn't resolve virtual-hosted-style bucket subdomains (`<bucket>.localhost:4599`) the way real S3 does. Fixed by adding `s3_use_path_style = true` to both `provider.tf` files (main and bootstrap) and `use_path_style = true` to `backend.hcl.example`. Documented in `infra/README.md`.
- Main `infra/`: `terraform init -backend-config=backend.hcl` against the bootstrap-created bucket/table succeeded — confirms the S3-backend mechanism (init, state read/write, DynamoDB locking) works end-to-end against a single LocalStack container. `terraform validate` and `terraform plan` both clean (52 resources planned, 0 errors).
- `terraform apply`: confirmed the five known Pro-tier gaps from ticket 11 still apply unchanged (ECS, ECR, RDS, ElastiCache, ELBv2 — all 501 "not yet implemented or pro feature"). Found one new Pro-tier gap: **CloudFront** (`aws_cloudfront_origin_access_control` and, transitively, `aws_cloudfront_distribution`) — also 501. Contrary to the ticket's assumption, **Route53, ACM, and S3 are not Pro-gated** — `aws_route53_zone`, the DNS validation record, `aws_acm_certificate`, and `aws_acm_certificate_validation` all applied and completed successfully, including the real DNS-validation round-trip.
